                bityard edited 2026-10-20 11:26:36

                Copying private keys away from the machine they were generated on is generally to be avoided. You could accidentally leave them somewhere you don't mean to (temp directory, thumb drive), or someone could steal/pwn one of your machines.

                SSH certificates are the solution you're looking for. You can set up a CA and then sign both host and user public keys with it. This avoids having to share/distribute user keys, and also solves the weakness of trust-on-first-use when connecting to a host for the first time. (Literally nobody verifies key fingerprints.) Setting up the CA and then using it to sign keys is of course a little work the first time but it can be automated.

                    colonelpanic edited 2026-10-20 17:28:06

                    "set up a CA" is really simple.

                    ssh-keygen -t ed25519 -f certificate_authority -C "User Certificate Authority"

                    copy to server and add this to your sshd_config:

                    TrustedUserCAKeys /etc/ssh/certificate_authority.pub

                    Then you sign your ssh public key:

                    ssh-keygen -s certificate_authority -I $(uuidgen) -z '0001' -n username id_ed25519.pub

                    ssh config:

                    Host server01
	User username
	IdentitiesOnly yes
	IdentityFile ~/.ssh/id_ed25519
	CertificateFile ~/.ssh/id_ed25519-cert.pub

                    atmosx 2026-10-20 08:42:28

                    1P can be used to generate or save existing ssh keys. The app knows that the type of secret is an ssh key. There's a background agent that needs to be enabled. At that point you just configure the IdentityAgent socket:

                    IdentityAgent "~/Library/Group Containers/ABC.com.1password/t/agent.sock"

                    Then the SSH agent will trigger a touchID authentication during session init and wait for your fingerprint. The data is synced via cloud, so when I setup a new machine, all I have to do is setup 1P via mobile QR code and I have access to all my private keys.

                    See: https://www.1password.dev/ssh

                        tonyarkles 2026-10-20 17:14:38

                        I ran into a similar question a while ago when trying to do something similar using a Yubikey as an SSH key. The procedure used in the blog post here generates the key in-enclave, which is the most secure from a privacy perspective (if it has never left the secure enclave it can't be intercepted) but not the most secure from an availability perspective (you don't have a way to back it up).

                        On the Yubikey side, my strategy was to generate the key off-Yubikey, back it up (I put it on a USB drive with a passphrase and then put it in my safe), and then load it onto the Yubikey. Slight tradeoff here in that the key does exist in memory in plaintext at one point, so technically open to interception by malware or whatever, but I do get a backup of it.

                        I haven't tried it, but based on what was in the blog post I looked at the man page for sc_util and it does have import-ctk-identities and import-ctk-certificate sub-commands as well. The import-ctk-identities sub-command explicitly has a flag to specify how the private key is protected inside the PKCS#12 archive, so that at least suggests to me that you could do a similar flow where you generate a private key, import it into the enclave, and then delete the key material from your machine (or remove the media the key is stored on).
